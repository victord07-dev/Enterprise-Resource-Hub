# Multi-Brand Product Catalog & Bulk Import

## What & Why
ITFI Group distributes solar/electronics products from multiple brands (Eastman, Luminous today; Adani Solar, Tata Solar, Vikram, Waaree next). The current Products module is generic — single GST default, free-text brand, four placeholder categories, no specs, no MRP, no bundles, no bulk import. Sales staff cannot quote correctly across brands and accounts cannot file GST cleanly because product master data does not capture brand-specific reality.

This ticket builds the foundation for a multi-brand catalog that absorbs Eastman + Luminous now and any future brand whose categories already exist in the 16-category list with a CSV paste — no code change. (A genuinely new category type — say a brand introducing "Wind Inverter" — will require a category list addition; that's a one-line code change, not a deploy.) It also lands the two things that cannot be retrofitted later (customer-type classification and ALMM/DCR flags on panels), the bundle/kit engine for BOS Kit + Lith Combo + SPGS, and a brand-agnostic CSV bulk-import. Six cheap schema additions (`distributorPrice`, `customerTierPrice`, `modelSeries`, `lifecycleStatus`/`replacedByProductId`, `applicableRegions`, `priceListVersion`) future-proof every onboarding from brand #3 onwards.

Strategic boundary: this is a catalog ticket. Tier/volume pricing, customer regional pricing, manufacturer rebates, MRP hard-block, brand credit terms, and PO unit-cost source consistency are explicitly deferred to later tickets. **Per-unit serial-number tracking is excluded entirely** — ITFI does not process returns, so serials provide no operational value.

## Done looks like
- [ ] Brands managed from a master list. Admin can add any new brand with one row, no code deploy. Every product links to a brand by FK; brand is mandatory.
- [ ] Product form uses the 16-category cross-brand list. Category change auto-fills GST + HSN. Manual override shows "Non-standard rate — verify with CA before invoicing."
- [ ] Product form captures: `distributorPrice` (brand's published price), warranty, MRP, ALMM, DCR, pack size, model series, lifecycle status, applicable regions, price-list version, and per-product tier prices (distributor / dealer / sub-distributor / scheme) as a key-value grid.
- [ ] **When the user enters `distributorPrice` on the form, `unitPrice` auto-populates with `distributorPrice × (1 + minMarginPct/100)` as a safe-floor selling price; user can override.** The same auto-compute runs during CSV import when `unitPrice` is blank.
- [ ] `replacedByProductId` field is conditionally visible only when lifecycle status = Replaced.
- [ ] `modelSeries` autosuggest is scoped to the same brand + category combination.
- [ ] Dynamic specs editor shows category-appropriate fields plus a "+ Add Custom Field" button. Custom keys appearing in 3+ products of the same category auto-promote to suggested fields, **counted in a server-side `custom_field_usage_stats` table** so all admins see the same suggestions.
- [ ] Customer record carries `customerType` (distributor, dealer, end_user, project, govt). **Migration produces a per-customer mapping report (current customerType + suggested customerType + customer name + outstanding balance) for the operator to eyeball; operator can override individual rows in the report before commit.** Default mapping: B2C → end_user, B2B → dealer, anything else → end_user, but every row is reviewable. Coloured badge on customer list and sales header (matches existing customer status badge pattern; no new colour scheme).
- [ ] Sales / quotation line items show ALMM ✓/✗ and DCR ✓/✗ chips on solar panels. **Subsidy-tagged order with non-ALMM panel triggers an inline blocking warning: "This panel is not ALMM-listed. If the subsidy scheme requires ALMM (most schemes do), the application will be rejected."** Soft warning when selling price exceeds MRP for an end_user customer. Tier price reference visibly displayed next to the unit-price input. Quotation PDFs include warranty period below each line.
- [ ] **New warnings apply only to newly-edited line items.** Existing draft quotations created before Phase 5 deploy do NOT retroactively raise warnings on lines that were already saved.
- [ ] Admin can bulk-import products from a downloadable CSV template. **Import has explicit Dry Run vs Commit modes:** Dry Run parses, validates, shows the import preview (would-import, would-skip, errors, duplicate-SKU-within-file warnings) and writes nothing. Commit performs the import inside a single transaction. Per-row error report downloadable as CSV with columns {row_number, sku, product_name, error_type, error_message}.
- [ ] **CSV import auto-creates `supplier_products` link rows:** when a row's brand name matches an existing supplier name (case-insensitive), a `supplier_products` row is created with `supplierPrice = distributorPrice`, `supplierSku` from the CSV column if provided else NULL, `isPrimary = true` unless another isPrimary link already exists for that product (in which case false).
- [ ] **Within-file duplicate SKU detection:** if the uploaded CSV itself contains the same SKU twice, Dry Run flags the duplicates and the operator decides whether to abort and fix the CSV, or proceed accepting that only the first row will be imported.
- [ ] Bundle products are first-class. Components defined in product form. Manual or auto-calculated pricing. **Bundle dispatch is atomic: stock deduction from every component happens in the same transaction as the delivery challan; if any component is short, the entire dispatch fails with an error listing all insufficient components, no partial deductions.** Insufficient-stock warning per component on the quotation. Nightly job flags any auto-priced bundle whose computed price drifted >2% since yesterday.
- [ ] **Bundle component lifecycle awareness:** if any component product has lifecycleStatus ≠ 'active', the parent bundle is auto-flagged with `needsPricingReview = true` and a visible warning "Component [name] is [status]" appears on the bundle's product detail.
- [ ] Catalog loaded in this strict order: (1) Eastman non-bundle products, (2) Luminous non-bundle products, (3) **STOP — verify Phase 7 bundle engine end-to-end with one real bundle dispatched and stock_movements rows confirmed**, (4) Eastman Lith Combos, (5) Luminous SPGS combos. No shortcuts past the Phase 7 verification gate.
- [ ] **Pre-Phase-8 cleanup acknowledged:** before first CSV import, operator has reviewed the existing product list and deactivated/deleted any seed or test-product entries (e.g., "Test Product 1") to avoid contaminating the live catalog. This is operator pre-work, not agent work.
- [ ] **Final verification suite passes:** (a) 10 sample mixed-brand quotations spot-checked against original price lists with GST totals matching, (b) one full bundle dispatch end-to-end with stock deduction from each component verified in stock_movements, (c) discontinued and replaced products do not appear in the Sales line-item picker, (d) creating a sales order with an existing pre-#74 non-branded product still works (regression), (e) GRN against an existing pre-#74 PO still works (regression), (f) Daily Pricing engine still computes a non-zero blended cost for an existing product with a confirmed GRN lot (regression — confirms the engine wasn't disturbed).
- [ ] All existing modules (Products list, Sales/Quotations, Daily Pricing, Inventory/GRN, Reports, SupplyChain) continue to work — every new column is NULL/default, no existing column or API renamed or removed.

## Out of scope
- **Per-unit serial-number tracking and the `product_serials` table** — ITFI does not process returns; serials provide no operational value and would only burden GRN entry.
- Volume / tier / pallet quantity pricing engine — separate ticket.
- Customer regional pricing logic and `customers.deliveryRegion` column — separate ticket.
- Manufacturer rebate / volume incentive tracking — separate ticket.
- RGP (defective return to supplier) flow — not relevant; no returns business.
- MRP hard-block (admin-configurable allow / warn / block per customer type) — soft-warn only here.
- Brand-level credit terms / payment terms / cash-discount % — belongs in supplier-ageing module.
- Per-(brand, category) spec template overrides and sub-brand hierarchy (Adani Mundra vs Goldi) — premature; revisit when a real case appears.
- Subsidy-scheme matching beyond the single ALMM/DCR check (PM Surya Ghar, MNRE, KUSUM full eligibility logic). ALMM list quarterly refresh process is also out of scope; for now the operator updates the ALMM flag manually per product when the brand notifies them.
- Brand approval workflow for new product entries.
- PDF parsing of brand price lists. Bulk import is CSV/Excel only; PDFs stay as reference for the operator filling the template.
- State-level `applicableRegions` (region-level only here; state-level can be added later if a state-restricted brand is onboarded).
- Mobile/tablet responsive testing of the new tier-price reference panel — sales reps quote on desktop today; defer until that changes.
- Per-bundle configurable price-drift threshold (single 2% global default here; configurable per-bundle deferred to a future ticket if real use shows 2% is wrong).
- **PO unit-cost source consistency fix** (sales-order-driven auto-purchase-request currently uses `products.costPrice` instead of `supplier_products.supplierPrice`) — separate ticket #75 to be raised after #74 lands.
- Any change to the existing Daily Pricing engine, Inventory/GRN logic, Sales totals math, audit trail, or auth — additions only, no behaviour changes.

## Steps

1. **Phase 1 — Schema foundation (additive, non-breaking).** Add `brands` table (id, name unique, defaultMarginPct, gstOverrideAllowed, notes, isActive). Seed Eastman, Luminous, Adani Solar, Tata Solar, Vikram Solar, Waaree. Add to `products`: `brandId` (FK NULL), `distributorPrice` (DECIMAL(10,2) NULL), `warrantyPeriod`, `mrp`, `specs` (JSONB NULL), `packSize`, `almm`, `dcrCompliant`, `modelSeries`, `lifecycleStatus` (default 'active'), `replacedByProductId` (self-FK NULL), `applicableRegions` (text[] NULL — NULL = all India; convention documented as a column comment), `priceListVersion`, `customerTierPrice` (JSONB NULL). Add `product_bundle_items` table. Add `custom_field_usage_stats` table (category, key, count). Extend `customers.customerType` valid values to {distributor, dealer, end_user, project, govt}. **Migration discipline:** take a fresh DB backup, write the migration as a SELECT first that produces a per-customer mapping report (id, name, current customerType, suggested new customerType, outstanding receivable balance), present the report to the operator, allow the operator to override individual rows, and only then run the UPDATE inside a single transaction. Existing products default to NULL specs (no backfill). Run `npm run db:push --force`. **Smoke test gate:** Products list, Sales line-item product picker, Daily Pricing page, GRN page, SupplyChain page must all load without error. Stop and confirm with user before Phase 2 if any module breaks.

2. **Phase 2 — Products form, brand master, GST/HSN auto-defaults.** Replace free-text brand input with a Select sourced from `GET /api/brands` plus inline "Add new brand" mini-dialog; brand becomes required. Replace placeholder categories with the unified 16-category list. On category change, auto-populate GST + HSN; show a warning icon if the user then overrides GST. Extend unit options to {pcs, kg, ltr, mtr, box, set, WP, Ah, KWh}. Add form fields: `distributorPrice` (number), `unitPrice` (number, **auto-fills as `distributorPrice × (1 + minMarginPct/100)` whenever distributorPrice changes and unitPrice is empty or matches a previous auto-value; user override sticks**, with a small visible "(auto: ₹X)" hint), warranty, MRP (non-service only), ALMM/DCR (panels only), pack size, model series (text input with autosuggest scoped to same brand + category), lifecycle status (Select: Active / Discontinued / Replaced / Draft), `replacedByProductId` as a product search field shown only when lifecycle status = Replaced, applicable regions as multi-select chips with options {All India, North, South, East, West, Northeast} (NULL stored when "All India" selected), price-list version (text input, auto-stamped on CSV import), and `customerTierPrice` as a simple key-value grid with preset rows {distributor, dealer, sub-distributor, scheme}. Add Brand and Warranty columns to the products table; show ALMM/DCR chips on panel rows; show a discreet "Discontinued" badge on non-active lifecycle rows. **Filter the Sales line-item product picker to exclude lifecycle = discontinued / replaced.** Add **Zod schema validators in the storage layer** for `customerTierPrice` and `specs` JSONB columns to enforce shape (numeric values, no string-as-number drift).

3. **Phase 3 — Customer-type field + sales header surface.** Render Select on customer form (Distributor / Dealer / End User / Project / Govt) and a coloured badge in the customer list and on the Sales / Quotation header next to the customer name; badge style matches existing customer status badge pattern. No price logic yet — that lands in Phase 5.

4. **Phase 4 — Dynamic Specs editor.** New file `client/src/constants/categorySpecTemplates.ts` with typed templates (number / text / select with options) for the 12 spec-stable categories, namely: Solar PCU — Sine Wave, Solar PCU — MPPT, Grid Tie Inverter — 1 Phase, Grid Tie Inverter — 3 Phase, Hybrid Inverter, Home UPS / Inverter, Solar Battery — Lead Acid, Solar Battery — Lithium, Home Battery — Lead Acid, Rack / Wall Battery, Solar Panel / PV Module, Solar Charge Controller. The four kit/accessory categories (GTI Accessory, Inverter Accessory, Solar BOS Kit, Solar Combo / SPGS) use custom-fields only. New `SpecsEditor` component: renders template fields + saved custom keys + "+ Add Custom Field" rows + Remove buttons; **on save, increments `custom_field_usage_stats(category, key, count)` server-side**; on render, queries that table and shows any (category, key) with count ≥ 3 as a suggested field. Embed in product dialog for non-service products; persist as JSONB; show a "Specs" badge with hover tooltip in the products table.

5. **Phase 5 — Sales module surfaces (warnings only, no blockers on the order itself).** On a Solar Panel line item, render ALMM ✓/✗ and DCR ✓/✗ chips. Add a `subsidyScheme` field on Sales Orders (Select: none, PM Surya Ghar, MNRE Rooftop, KUSUM, Other); when scheme ≠ none and panel is not ALMM, show inline warning "This panel is not ALMM-listed. If the subsidy scheme requires ALMM (most schemes do), the application will be rejected." On unit-price change, soft-warn if `unitPrice > mrp` and customer type = end_user; informational note for dealer/distributor. Render a small reference panel next to the unit-price input showing the product's `customerTierPrice` values. Include `warrantyPeriod` line under each item in jsPDF quotation output. **Warnings fire only on lines that are newly added or edited after the Phase 5 deploy; pre-existing draft lines stay quiet** (gate keyed on whether the line's `lastEditedAt` precedes the deploy timestamp, or simpler equivalent — exact check decided at implementation time). **Stop gate end of Phase 5:** commit, push, then operator manually verifies — (a) ALMM chip renders on a panel line, (b) subsidy scheme warning fires when scheme is set + panel non-ALMM, (c) MRP soft-warn fires for end_user with unit_price > mrp, (d) tier-price reference panel displays for a product with customerTierPrice values, (e) warranty appears on quotation PDF, (f) pre-existing draft quotation does not surface new warnings on its old lines. Only after these six pass does Phase 6 start.

6. **Phase 6 — Bulk CSV import.** New `POST /api/products/import` (multipart, CSV file, `mode=dry_run|commit` query param). CSV columns: name, sku, brand, category, description, distributorPrice, unitPrice, gstRate, hsnCode, unit, minStockLevel, minMarginPct, warrantyPeriod, mrp, type, packSize, almm, dcrCompliant, modelSeries, lifecycleStatus, applicableRegions, priceListVersion, customerTierPrice (JSON), specs (JSON), supplierSku. Required: name, category. Validate category against the 16-list; auto-create missing brands; never overwrite existing SKU (skip + report); auto-generate SKU when blank from brand+name+timestamp. **Within-file duplicate SKU detection:** in Dry Run, surface duplicates explicitly. If `unitPrice` is blank but `distributorPrice` is present, auto-compute `unitPrice = distributorPrice × (1 + minMarginPct/100)` (per-product `minMarginPct`, falling back to a per-import-dialog default). Auto-stamp `priceListVersion` from a single field at the top of the import dialog if the CSV column is empty. **Auto-create `supplier_products` link** when row brand name matches an existing supplier name (case-insensitive): `supplierPrice = distributorPrice`, `supplierSku` from CSV, `isPrimary = true` unless another isPrimary link already exists for the product (then false). Wrap commit-mode inserts in a single transaction; dry-run writes nothing. Return `{mode, imported, skipped, errors[], duplicates[]}`. Frontend: "Import CSV" button next to "+ Add Product"; dialog with file picker, optional "Price List Version" text field, optional "Default Min Margin %" field, **explicit Dry Run vs Commit toggle**, Download Template link with one example row each for Solar Panel / PCU / Battery / Accessory (other categories use the same columns), preview/validation step that shows would-import / would-skip / errors / duplicates, results summary, downloadable error CSV with columns {row_number, sku, product_name, error_type, error_message}. **Stop gate end of Phase 6:** commit, push, then operator runs a real-data validation — (a) Dry Run a 5–10 row real Eastman CSV slice, confirm preview shows correct would-import counts and any expected duplicate-SKU warnings, (b) Commit the same slice, confirm rows land with correct distributorPrice, auto-computed unitPrice, GST/HSN auto-fill, (c) confirm a `supplier_products` link row was auto-created for each imported product whose brand matches an existing supplier name, with `supplierPrice = distributorPrice`, (d) deliberately upload a row with an invalid category and confirm error CSV downloads with correct columns and row numbers, (e) re-upload a row with an existing SKU and confirm it is skipped (not overwritten). Only after these five pass does Phase 7 start.

7. **Phase 7 — Bundle / kit engine.** Add 'bundle' as a valid value for `products.type`. UI: Components section in product form (add/remove rows of {component product, qty, unit}), Pricing Mode toggle (Manual fixed price / Auto = sum of component effective prices). On Sales Order line-item save, show insufficient-stock warning per component on the quotation. **On dispatch, the entire stock deduction across all components happens inside the same transaction as the delivery challan creation.** If any component is short at dispatch time, the entire dispatch fails with an error listing every insufficient component; no partial deductions. Bundle itself holds no stock. **If any component product has `lifecycleStatus ≠ 'active'`, the parent bundle auto-sets `needsPricingReview = true` and shows a visible warning on the bundle detail page.** **Internal stop gate:** verify bundle dispatch end-to-end with one real bundle, one real challan, and confirm `stock_movements` rows for each component before adding the cron. After verification, add the nightly node-cron job that recomputes price for every Auto-mode bundle from current effective prices and flags bundles whose computed price moved >2% by setting `needsPricingReview = true`.

8. **Phase 8 — Catalog load + final verification.** Pre-work (operator): clean up seed/test-data products from the existing catalog. Then load in this strict order: (1) Eastman non-bundle products via CSV, (2) Luminous non-bundle products via CSV, (3) **verify Phase 7 bundle engine end-to-end** if not already verified during Phase 7 internal gate, (4) Eastman Lith Combos as bundle products, (5) Luminous SPGS combos as bundle products. Run the final verification suite: (a) spot-check 10 mixed-brand quotations against original price lists — GST totals must match, (b) execute one full bundle dispatch end-to-end and confirm stock_movements show the correct per-component deductions, (c) verify the Sales line-item picker excludes discontinued and replaced products, (d) regression: create a sales order with an existing pre-#74 non-branded product, (e) regression: receive GRN against an existing pre-#74 PO, (f) regression: confirm Daily Pricing engine returns a non-zero blended cost for an existing product that has a confirmed GRN lot. Only after all six pass is the ticket Done.

Architectural constraints:
- Every new column is NULL or has a DEFAULT. Never make a new column NOT NULL without a default.
- Do not modify existing column names, types, or remove existing fields. Do not change existing API endpoint signatures or response shapes.
- Each phase commits and pushes. **Mandatory user verification gates** at: end of Phase 1 (smoke test), inside Phase 7 (bundle dispatch before cron), end of Phase 7 (full bundle flow before Phase 8). Other phases proceed straight through unless something breaks.
- Keep pricing/margin logic untouched — daily pricing engine reads new columns only when explicitly told to.
- **The nightly cron job in Phase 7 is the one permitted addition to `server/index.ts` in this ticket. No other changes to that file.**
