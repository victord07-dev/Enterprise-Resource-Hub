#22 — Lot Engine: Schema & FIFO API
What & Why
Solar panels, electronics, and commodity products arrive in discrete purchase batches (lots) with different landed costs. The current system uses a single weighted-average cost (WAC) on the product record, which is correct for financial and accounting reporting but too coarse for daily pricing decisions. This task adds the schema and a FIFO-based lot engine API that computes per-lot remaining quantity, landed cost, and floor prices — the foundation every other feature in this feature set depends on.

Cost Strategy (mandatory rule — executor must follow)
WAC on product.costPrice — remains unchanged. Continues to be updated on each GRN confirmation and used for accounting, AP, and financial reports. Never touch this in the lot engine.
FIFO via lot engine — used exclusively for pricing decisions and margin calculation. Runs in parallel to WAC. Never replace WAC with FIFO in accounting flows. These are two separate systems serving two separate purposes.

Done Looks Like

GET /api/inventory/stock-lot-summary?productId=&warehouseId= returns a correct lot breakdown. Each GRN lot shows its remaining quantity, landed cost (buying price + allocated delivery cost), and lot floor price. The response also includes blendedCost, globalFloor, and strictFloor.
Products admin page shows an editable minMarginPct field and a read-only needsPricingReview badge.
Delivery challan dispatch creates one stock_movements row per GRN lot consumed (not one aggregate row), each row carrying that lot's grnId and the quantity consumed from it. FIFO determines allocation order.
RETURN_IN movements from sales returns carry grnId traced from the original dispatch movement (challan_item → dispatch movement with grnId), not a best-effort guess. See V1 deviation note below.

Pricing Field Definitions (mandatory clarity)
proposed_market_price (sheet level):
The single final selling price for the day. Entered by the user at the sheet level. Returned by the effective-price API. Used by sales order and quotation forms to auto-populate unit price.
proposed_price (per lot, in daily_price_sheet_lots):
Used only for override floor validation. Compared against lot_floor_price to set override_required. Not used as the final selling price. Not returned to sales forms.

Lot Engine: Movement Replay Rules
Sort order (mandatory, correctness-critical)
All movements must be loaded and replayed in this order:
ORDER BY created_at ASC, id ASC
id is the tie-breaker for movements created within the same timestamp. Wrong sort order produces wrong FIFO allocation, which produces wrong margins. This is not a preference — it is the definition of FIFO correctness in this system.
Movement type handling
GRN / STOCK_IN where reference_type = 'grn':
Create a new lot. Set remaining_qty to the received quantity. Compute landed_cost per the formula below. Set grn_id from the movement's grn_id column; if null (old data), use reference_id as fallback.
DISPATCH / STOCK_OUT where reference_type = 'challan':
Consume FIFO. Deduct from the oldest lot with remaining_qty > 0 first. If the oldest lot doesn't cover the full quantity, continue to the next oldest. Skip any lot where remaining_qty = 0 — treat it as exhausted and move on without error.
RETURN_IN:
If grn_id is present, restore quantity to that specific lot. If grn_id is null (old data), assign to the oldest currently-depleted lot (best-effort for historical data only).
ADJUSTMENT_IN:
Create a synthetic lot. Set landed_cost = product.costPrice. Set grn_id = NULL. This is expected — synthetic lots have no GRN origin.
ADJUSTMENT_OUT:
Consume FIFO, same logic as dispatch.
PURCHASE_RETURN:
typescript// PURCHASE_RETURN: will reduce from original lot — reserved for future module
Skip for now. Do not throw an error.
Landed cost formula
allocated_delivery_cost = grn.delivery_cost × (line_item_qty / total_grn_qty)

landed_cost = (buying_price × qty + allocated_delivery_cost) / qty
If grn.delivery_cost is null or zero, allocated_delivery_cost = 0 and landed_cost = buying_price.
Floor price formulas
lot_floor_price  = landed_cost × (1 + min_margin_pct / 100)

blended_cost     = SUM(remaining_qty × landed_cost) / SUM(remaining_qty)

global_floor     = blended_cost × (1 + min_margin_pct / 100)

strict_floor     = MAX(lot_floor_price) across all remaining lots
blended_cost is a quantity-weighted average. A lot with 100 units at ₹50 has more weight than a lot with 5 units at ₹80. Do not compute it as a simple average of landed costs.
If SUM(remaining_qty) = 0 across all lots (all stock depleted), return blended_cost = null, global_floor = null, strict_floor = null. Do not divide by zero.

V1 Return Deviation (explicitly documented)
The RETURN_IN grnId resolution for new returns follows this rule: if multiple lots were consumed for the same line item, assign the return to the most recently consumed lot's grnId.
This is a known, intentional deviation from pure FIFO returns (which would proportionally restore across all consumed lots). It is a V1 simplification accepted for implementation speed.
Place this comment at the RETURN_IN movement creation in the sales return handler:
typescript// FIFO DEVIATION (V1): Return assigned to most recently consumed lot when multiple
// lots were consumed for this item. True proportional allocation deferred.
// TODO: Support proportional return allocation across multiple lots.

Dispatch: Per-Lot Movement Splitting (architectural change)
When a delivery challan is dispatched, the existing dispatch handler must be refactored:
BEGIN TRANSACTION

  1. Call lot engine to determine FIFO allocation
     → returns: [ { grnId, qtyToConsume }, ... ]

  2. For each lot in the allocation:
     INSERT INTO stock_movements (product_id, grn_id, qty, movement_type, ...)
     VALUES (productId, lot.grnId, lot.qtyToConsume, 'DISPATCH', ...)

  3. UPDATE inventory_stock
     SET total_qty = total_qty - totalDispatchedQty
     WHERE product_id = productId AND warehouse_id = warehouseId
     -- Use total dispatched qty, not per-lot — balance is at product level

COMMIT

On any error → ROLLBACK
No partial writes permitted under any circumstances.
Invariant to verify in testing: SUM(qty across all movement rows for this dispatch) = total dispatched quantity. Write a test for this.
