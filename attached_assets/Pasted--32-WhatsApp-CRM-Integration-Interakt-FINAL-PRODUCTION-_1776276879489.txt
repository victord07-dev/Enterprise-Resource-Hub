#32 — WhatsApp CRM Integration (Interakt) (FINAL, PRODUCTION-READY)
What & Why
Integrate Interakt's WhatsApp Business API into the ERP so employees can conduct
sales conversations, send quotations/invoices, run bulk campaigns, and receive
automated owner alerts — all without leaving the app.
This transforms the system from a pure ERP into an ERP + CRM + WhatsApp sales channel.

Done Looks Like

A full-featured /inbox page exists in the sidebar (visible to admin,
sales_manager, field_staff) showing a list of WhatsApp conversations on the
left, a live chat window in the centre, and a customer timeline panel on the right.
Within the chat window, employees can type and send free-text messages (when
the 24-hour session window is open) or send approved template messages at any
time. A banner is shown when the window is closed.
A "Send via WhatsApp" button on each quotation/sales order opens a modal
to pick a template, preview it, and send via Interakt.
A /campaigns page (sidebar: admin + sales_manager) lets the user select
customers, pick a template, and send bulk WhatsApp messages in rate-limited batches.
A /settings/whatsapp-templates page (admin only) allows creating, editing,
and deleting internal template records.
A CRON job fires at 09:00 and 18:00 daily, sending a summary WhatsApp alert
to all admin phone numbers.
Incoming messages from Interakt arrive at POST /api/whatsapp/webhook and are
persisted to the DB; the inbox polls every 10 seconds to show them.
Message delivery status (sent / delivered / read / failed) is shown with tick
indicators (✓ / ✓✓ / ✓✓ blue / ✗) in the chat window.
Conversations support assignment, internal notes, and conversation tags.
Opening a conversation in the inbox immediately resets its unread count to zero.


Out of Scope

AI chatbots or automated conversation flows
WhatsApp analytics dashboard
Multi-language bot responses
Green-tick verification (handled on Meta/Interakt side)
Interakt contact sync (customers managed in existing tables)
Campaign scheduling, drafts, and partial retry


Architecture Notes
Provider

Security (MANDATORY — two layers):

HMAC Signature Verification (primary):
Interakt sends an X-Interakt-Signature header containing an
HMAC-SHA256 signature of the raw request body, signed with your
webhook secret. Verify this on every incoming request:

typescript   import crypto from 'crypto';

   function verifyInteraktSignature(
     rawBody: Buffer,
     signature: string,
     secret: string
   ): boolean {
     const expected = crypto
       .createHmac('sha256', secret)
       .update(rawBody)
       .digest('hex');
     return crypto.timingSafeEqual(
       Buffer.from(expected),
       Buffer.from(signature)
     );
   }

   // In webhook route — use express.raw() to get raw body for HMAC:
   // If verification fails → return HTTP 401, log the attempt, do not process.

Token query param (secondary):
Also verify ?token=<WHATSAPP_WEBHOOK_TOKEN> query param as a
secondary layer. Reject if missing or mismatched.

Phone Number Normalisation (MANDATORY — apply everywhere)
WhatsApp numbers must be in E.164 format: digits only, with country code, no +.
Example: +91 98765 43210 → 919876543210
Create a utility in server/whatsapp.ts:
typescriptexport function normalisePhone(raw: string): string {
  // Strip all non-digit characters
  const digits = raw.replace(/\D/g, '');
  // If Indian number entered without country code (10 digits starting with 6-9)
  if (digits.length === 10 && /^[6-9]/.test(digits)) {
    return `91${digits}`;
  }
  return digits;
}
Apply normalisePhone() on:

Webhook inbound: before looking up customer by phone
Outbound send: before calling Interakt API
Campaign fan-out: before each recipient send
CRON alerts: before sending to admin phones

All phone numbers stored in whatsapp_conversations must be normalised.
Run normalisePhone() at write time, not read time.

Conversation Lifecycle (CRITICAL — follow exactly)
Inbound message arrives at webhook:
1. Verify HMAC signature → reject HTTP 401 if invalid
2. Verify ?token query param → reject HTTP 401 if invalid
3. normalisePhone(incoming phone number)
4. Look up customer WHERE normalisePhone(phone) = normalisedPhone
5. Search for conversation WHERE status = 'open'
   AND (customerId matches OR phoneNumber matches)

   IF found:
     - Add message to that conversation
     - Set windowExpiresAt = NOW() + 24 hours
     - Increment unreadCount + 1
     - Update lastMessageAt = NOW()

   IF NOT found:
     - Create new conversation with status = 'open'
     - Set customerId = matched customer id (or NULL if no match)
     - Set phoneNumber = normalised incoming phone
     - Set windowExpiresAt = NOW() + 24 hours
     - Set unreadCount = 1
     - Add the inbound message to the new conversation
Rules:

Closed conversations are NEVER reopened. Always create a fresh one.
Only inbound messages extend windowExpiresAt. Outbound messages and
notes do NOT reset it.
On status → 'closed', set windowExpiresAt = NULL.
The manual POST /api/whatsapp/conversations endpoint must NOT auto-create
conversations — it is for explicit admin creation only. If an open conversation
already exists for the same customer, return it (HTTP 200) instead of creating
a duplicate.


Unread Count Behaviour

Incremented by 1 on the conversation row on every inbound webhook message.
When an employee opens a conversation (selects it in the left panel), the
frontend immediately calls:

  PATCH /api/whatsapp/conversations/:id  { unreadCount: 0 }
The unread badge then disappears from the conversation list.

24-Hour Window
The UI checks windowExpiresAt > NOW() to decide:

Window open: show free-text composer + template button
Window closed/null: show "24-hour window closed — use a template" banner +
template-only button

Only inbound messages extend the window.

Notes vs Messages
Internal notes:

direction = 'outbound', type = 'note'
Never sent to Interakt
Displayed in chat window with yellow background and 🔒 label
Visible to employees only


PDF Attachment via WhatsApp
Interakt's document message type requires a publicly accessible URL.
Client-side jsPDF blobs cannot be used.
Flow:

Frontend calls POST /api/whatsapp/generate-pdf with document type and ID.
Backend first verifies the requesting user has read access to that document
(apply the same role checks as the existing quotation/invoice GET endpoints).
Return HTTP 403 if not authorised.
Backend generates PDF server-side, uploads to Replit Object Storage
(follow same pattern as server/attachments.ts), returns a public URL.
Frontend sends that URL to Interakt as a Document type message with filename.


Direct Send Rate Limiting
POST /api/whatsapp/conversations/:id/send must enforce server-side:
If more than 20 messages are sent to the same conversationId 
within a rolling 60-second window → return HTTP 429.
Use an in-memory counter keyed by conversationId (acceptable for single-instance
deployment). Add a // TODO: move to Redis at scale comment at the counter logic.

Campaign Rate Limiting
POST /api/whatsapp/campaigns/send must:

Process recipients in batches of 10
Apply a 100ms delay between batches
Return a per-recipient result array:

json  [
    { "customerId": "...", "phone": "...", "status": "sent" },
    { "customerId": "...", "phone": "...", "status": "failed", "error": "..." }
  ]
Campaign scheduling, drafts, and partial retry are out of scope.
