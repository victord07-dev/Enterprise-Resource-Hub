#74 — Multi-Brand Product Catalog & Bulk Import
FINAL PLAN (Serial tracking removed — no returns in business model)
Based on: Eastman (14 price lists) + Luminous (7 price lists) April 2026

═══════════════════════════════════════════════
WHAT & WHY
═══════════════════════════════════════════════

ITFI Group distributes solar products from multiple brands (Eastman and
Luminous today; Adani Solar, Tata Solar, Vikram Solar, Waaree next). The
current Products module is generic — single GST default, free-text brand,
four placeholder categories, no specs, no MRP, no bundles, no bulk import.

This ticket builds a multi-brand catalog that absorbs Eastman + Luminous
now and any future brand with a CSV paste — no code change required.

It also lands two things that cannot be retrofitted after go-live:
customer-type classification and ALMM/DCR flags on panels.

Five additional cheap schema fields (customerTierPrice, modelSeries,
lifecycleStatus/replacedByProductId, applicableRegions, priceListVersion)
future-proof every brand onboarding from brand #3 onwards.

Note: Serial number tracking is not required. ITFI Group does not process
returns, so product_serials table and serialTracked field are out of scope.

Strategic boundary: this is a catalog ticket. Tier/volume pricing, customer
regional pricing, manufacturer rebates, RGP defective returns, MRP hard-
block, and brand credit terms are explicitly deferred to later tickets.

═══════════════════════════════════════════════
TWO NON-NEGOTIABLE ADDITIONS NOT IN ORIGINAL DOCS
═══════════════════════════════════════════════

1. Brand master table (before any product is entered)
Do not hardcode brands as a dropdown. Create a brands table. Adding Adani
Solar or Waaree is then one INSERT row — no code deploy. Every product
links to brands.id as a foreign key, not a free-text field.

2. Per-product GST override with a warning
Category-level GST defaults are a starting point only. The Eastman 12% vs
Luminous 18% PCU disagreement proves this. Each product must be able to
override the default. When overridden, show: "Non-standard rate — verify
with CA before invoicing."

PHASE 5 — BULK CSV IMPORT
Effort: ~1.5 days | Risk: Low
═══════════════════════════════════════════════

Task 5.1 — POST /api/products/import endpoint in server/routes.ts
Accepts: multipart/form-data with a CSV file.

CSV columns (all optional except name and category):
  name, sku, brand, category, description, unitPrice, gstRate, hsnCode,
  unit, minStockLevel, minMarginPct, warrantyPeriod, mrp, type, packSize,
  almm, dcrCompliant, modelSeries, lifecycleStatus, applicableRegions,
  priceListVersion, customerTierPrice (JSON string), specs (JSON string)

Processing rules:
  - name and category are required; reject row if either is missing
  - category must exactly match one of the 16 valid values; reject if not
  - brand: if the brand name does not exist in the brands table, auto-create
    it with default settings
  - If SKU already exists in the database: skip the row and add it to the
    skipped list — NEVER overwrite an existing product
  - If SKU column is blank: auto-generate a slug from brand + name +
    timestamp
  - Set priceListVersion from the CSV column on every imported row
  - Wrap all inserts in a single database transaction
  - Return: { imported: N, skipped: M, errors: [{row: N, reason: "..."}] }

Task 5.2 — GET /api/brands endpoint
Returns all active brands ordered by name. Used by the brand Select in the
product form and for validation during CSV import.

Task 5.3 — Download Template
A downloadable sample CSV with all columns listed in Task 5.1. Include one
complete example row per major category type so the operator knows the
expected format and values for every field. This template is the standard
onboarding tool for every new brand going forward.

Task 5.4 — Import UI in Products page
Add an "Import CSV" button next to the existing "+ Add Product" button.
Opens a dialog with:
  - File picker (CSV only)
  - Download Template link
  - Column validation preview before the user confirms the import
  - Results summary after import: Imported N / Skipped M
  - Downloadable error report CSV if any rows failed validation

PHASE 6 — BUNDLE / KIT ENGINE
Effort: ~2-3 days | Risk: Medium
═══════════════════════════════════════════════

Interim workaround (use until Phase 6 is complete):
Enter BOS Kit as a single product at a fixed price. Enter each Lith Combo
and SPGS combo as a separate product SKU at the combo's total price. Stock
will not auto-deduct from components — track manually. This is functional
but should not be used for Luminous SPGS (500+ combos) because de-
duplication after the bundle engine ships will take weeks. Hold SPGS combos
until Phase 6 is verified live.

Task 6.1 — Add bundle as a valid product type
Add 'bundle' as a valid value for products.type alongside existing
'product' and 'service'.

Task 6.2 — Bundle components UI in product dialog
When type = bundle, show a Components section in the product form.
Add/remove component rows, each with: product selector, quantity, unit.
Show a Pricing Mode toggle:
  - Manual: fixed price set directly on the bundle product record
  - Auto: price = SUM(each component quantity × component effective price)
Both modes must be supported. BOS Kit uses Manual. SPGS combos use Auto.

Task 6.3 — Stock deduction on sale
When a bundle is added to a Sales Order or dispatched:
  - Deduct stock from each component product proportionally
  - The bundle itself holds no stock record of its own
  - If any component has insufficient stock, show a warning on the
    quotation: "Insufficient stock — [Component Name] is out of stock"
    before allowing the order to be confirmed

Task 6.4 — Nightly price freshness job
NOTE: This is the one permitted addition to server/index.ts in this ticket.
Add a node-cron job that runs nightly at 2:00 AM IST.

The job does the following:
  - Finds all bundle products with pricingMode = 'auto'
  - Recomputes the bundle price from current component effective prices
  - If the computed price has moved more than 2% since yesterday, sets
    needsPricingReview = true on that bundle product
  - These flagged bundles surface in the existing Daily Pricing Review
    screen automatically

This handles the Luminous SPGS 500+ combo situation. You do not need to
manually update 500 combo prices each time a component price changes.
