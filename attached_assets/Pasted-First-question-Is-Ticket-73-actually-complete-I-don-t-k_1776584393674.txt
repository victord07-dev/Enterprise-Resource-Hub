Architectural constraints
Schema conventions:

Use Drizzle ORM following existing patterns in shared/schema.ts
UUID PKs with varchar("id").primaryKey().default(sql\gen_random_uuid()`)`
Monetary fields: decimal('amount', { precision: 14, scale: 2 }) (note: 14 precision, not 12, for financial aggregation headroom)
Dates in IST. date columns as Postgres DATE; timestamps as TIMESTAMP WITH TIME ZONE
Text columns with Zod enums for enumerated values (account_type, transaction_type, direction) to match existing codebase convention — no pgEnum

Core table: transaction_ledger
Columns: id, transaction_date (DATE), value_date (DATE, for accrual vs cash-basis distinction), account_id (FK bank_accounts), direction (enum: debit / credit), amount (decimal 14,2), transaction_type (enum: invoice_issued / payment_received / supplier_invoice / supplier_payment / salary_disbursement / operational_expense / travel_reimbursement / credit_note / emi_payment / inter_account_transfer / bank_charge / interest_earned / owner_capital / tax_payment / manual_adjustment / opening_balance), counter_party_type (text, nullable), counter_party_id (varchar, nullable), counter_party_name (denormalized for reports, text), description (varchar 500), source_module (text), source_record_id (varchar), source_record_type (text, nullable), reference_number (text, nullable — for cheque numbers, UTR, etc.), created_by_user_id (FK), created_at, updated_at.
Indexes on transaction_ledger:

(transaction_date DESC)
(account_id, transaction_date DESC) — composite for per-account statements
(counter_party_id) — for per-customer / per-supplier statements
(transaction_type) — for filtered reports
(source_module, source_record_id) — for drill-down lookups

Table: bank_accounts
Columns: id, name (text), account_number (text, last 4 digits only or full — decide during implementation; favor full for reconciliation), bank_name (text), ifsc (text, nullable), account_type (enum: current / savings / overdraft / loan / cash), opening_balance (decimal 14,2), opening_balance_date (DATE), is_active (boolean default true), is_default (boolean, max one default per type), notes (text nullable), created_at, updated_at.
Table: loans
Columns: id, loan_number (text, unique), lender_name (text), lender_account_id (FK bank_accounts, nullable), principal_amount (decimal 14,2), interest_rate (decimal 5,2 — percent), interest_type (enum: fixed / floating), tenure_months (integer), emi_amount (decimal 14,2), emi_due_day (integer 1-31), disbursement_date (DATE), first_emi_date (DATE), last_emi_date (DATE, computed), current_outstanding (decimal 14,2, computed), status (enum: active / closed / defaulted), notes, created_at, updated_at.
Table: emi_schedule
Columns: id, loan_id (FK), installment_number (integer), due_date (DATE), principal_portion (decimal 14,2), interest_portion (decimal 14,2), total_emi (decimal 14,2), status (enum: pending / paid / overdue), paid_date (DATE nullable), paid_via_account_id (FK bank_accounts, nullable), ledger_entry_id (FK transaction_ledger, nullable — links back to the payment entry), notes nullable, created_at, updated_at.
Retrofit pattern (mandatory):
Every module retrofit follows this exact pattern:

Identify the single code path where financial event is created (e.g., createSalesInvoice, createCustomerPayment)
Add ledger write INSIDE the same transaction as the source record creation. Both must succeed or both must roll back.
Wrap ledger write in a helper function: writeLedgerEntry(tx, { ...fields }) — single helper shared across all retrofits. Do NOT duplicate ledger write logic.
Source module existing behavior must remain identical to before retrofit — same API response, same status codes, same side effects. Only addition is the ledger entry.
Add one integration test per retrofit: creating a source record must create exactly one ledger entry with correct fields.

Historical backfill:

Migration script per module. Idempotent (safe to re-run).
Each script: iterate all existing records in source table, write corresponding ledger entries if not already present.
Log counts: "backfilled 1,234 ledger entries for sales_invoices".
Reconciliation query after backfill: source table sum must match ledger sum per entity.
