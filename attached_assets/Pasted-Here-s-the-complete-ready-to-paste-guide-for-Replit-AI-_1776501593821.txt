Ticket #71 — Operational Expense Tracking (Phase 1: Entry + Visibility)
Context — please read before starting
This is a new feature, not a fix. The company currently has no system to track day-to-day petty/operational expenses — guest hospitality (tea/coffee/biscuits for visitors), loading/unloading charges, fuel, office supplies, software renewals, driver charges, labour charges during dispatch, etc. These expenses happen daily, are paid by various people (sometimes the CEO/Owner directly, sometimes employees upfront who later claim reimbursement), and currently go completely unrecorded. The CEO wants visibility into what's actually being spent, where, and by whom.
This ticket builds the foundational expense entry + visibility layer only. Deliberately light on workflow: no approvals, no petty cash balance tracking, no reimbursement workflow yet. Those are Phase 2 (separate future ticket) after we have a week of real-world usage data. The goal of this ticket is to get data flowing first — make recording effortless so adoption succeeds.

Decisions already made — do not re-open these

Placement: Expenses is NOT a top-level sidebar item. Two entry points only:

(a) A "Today's Expenses" summary card on the Dashboard with a "Record Expense" button.
(b) A new "Expenses" tab inside the existing Accounts page for full management.


Shared component: A single ExpenseDialog component is opened from both entry points — same form, same validation, same submit handler. Do not duplicate the form.
Relationship to existing travel expenses: Completely separate from the travel expense system in FieldStaff. Different tables, different flows, no merging, no linking. Travel expenses stay where they are. Field staff role does NOT see the new expense module.
Categories: 15 seed categories specified below. Stored in a database table, not hardcoded. Admins can add/rename/deactivate through a UI.
Category deletion: Soft-delete only (set is_active = false). Never hard-delete categories that have expenses against them.
Attachment storage: Reuse the existing attachments table + AttachmentsPanel component. Add expense to the allowed entity types list. Do not build new attachment code.
Linking to existing entities: Expenses can optionally link to a Sales Order / Delivery Challan / Customer / Project. These are optional — most expenses won't link anywhere. Do not make them required.

Done looks like
Dashboard

A "Today's Expenses" summary card appears on the Dashboard landing page, positioned below the existing "Today's Follow-ups" section.
Card visible to roles: admin, accountant, sales_manager, hr_manager, warehouse_manager. NOT visible to field_staff.
Card shows: today's total amount (₹), expense count, top category today (with amount), and a prominent "Record Expense" button.
Clicking "Record Expense" opens the shared ExpenseDialog component.

Accounts page

A new "Expenses" tab appears in the existing Accounts page tab strip, after the existing tabs.
Tab contains three sub-views (as internal tabs or sections): List view (default), Analytics, Categories (admin only).
List view has: summary cards at top, filters (date range, category multi-select, paid-by multi-select, payment mode, search), a "New Expense" button, a sortable table of expenses.
Analytics view has: 4 charts respecting the active date range filter.
Categories view (admin only) allows managing the expense category list.

Expense entry form

Required fields: date (defaults to today), category (dropdown), amount (₹), description (short text), payment mode (Cash / UPI / Card / Bank Transfer), paid_by (defaults to logged-in user; admin can pick another user).
Optional fields (collapsed by default behind a "+ Add more details" toggle): vendor/payee name, link to (Sales Order / Delivery Challan / Customer / Project) with dropdown powered by existing data, notes (long text), attachment upload.
Form validates before submit: amount > 0, category selected, description not empty, date not in the future.
On successful submit: closes dialog, shows toast, refreshes the list view if open, refreshes Dashboard card if that was the entry point.

List view filters

Date range filter with presets: Today / This Week / This Month / This Year / Custom range (date picker).
Category multi-select.
Paid-by multi-select.
Payment mode multi-select.
Free-text search on description.
Sort by: date (newest first, default) or amount (highest first).
All filters combine with AND logic. Filter state preserved in URL query params so it survives page refresh.

Summary cards (top of list view, update based on active filters)

Total amount for filtered range.
Expense count.
Top category (name + amount).
Highest single expense (amount + category).

Analytics tab (4 charts, all respecting the active date range filter)

By Category (horizontal bar chart, sorted descending by amount).
By Person (horizontal bar chart, who paid how much).
Daily Trend (line chart of daily totals over the selected range).
Category Share (pie chart showing percentage split).
Each chart has a sensible empty state if no data.

Category management (admin only)

List of all categories with name, active/inactive toggle, sort order.
Add new category.
Rename existing category.
Deactivate category (soft-delete).
Cannot rename or deactivate categories currently being used in this session's view (prevents mid-edit confusion) — this is a UX polish, not a data constraint.

Audit trail

Every expense create / update / delete writes an entry to the existing audit log table.
Module = expenses. Action = expense_created / expense_updated / expense_deleted.
Audit entry includes expense ID, amount, category, and user who performed the action.

Architectural constraints

New tables: expenses and expense_categories. Use Drizzle ORM, follow the existing patterns from shared/schema.ts (same column naming conventions, same timestamp patterns, same FK conventions).
No schema changes to existing tables except adding expense to the entity_type enum/check constraint on the attachments table.
Monetary precision: Use the same decimal precision as existing monetary fields in the codebase. Check existing tables for the convention.
Foreign keys: expenses.category_id → expense_categories.id (NOT NULL, ON DELETE RESTRICT). expenses.paid_by_user_id → users.id. expenses.created_by_user_id → users.id. Optional FKs for linked entities (nullable).
Indexes: On expenses(date DESC), expenses(category_id), expenses(paid_by_user_id), expenses(created_at DESC).
Shared dialog component: ExpenseDialog is the single source of truth for expense entry UI. Imported by both Dashboard card and Accounts tab. Do NOT duplicate form code.
Timezone: All dates stored and interpreted in IST. Date-only fields use DATE type, timestamps use TIMESTAMP WITH TIME ZONE.
No new third-party dependencies. Use existing libraries: Recharts for charts, Shadcn UI components, React Query for data, Drizzle for DB.
Audit logging uses the existing auditLog helper — do not build new audit infrastructure.
Migration for seed data: Seed the 15 default categories in a migration file, not in application code. Admins should be able to edit these freely without fighting code.
