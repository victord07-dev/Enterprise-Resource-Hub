Two Things Missing From Both Docs — Do These First
Brand master table (before any product is entered)
Do not hardcode brands as a dropdown in the form. Create a brands table with: id, name, defaultMarginPct, gstOverrideAllowed, notes. Seeded with: Eastman, Luminous, Adani Solar, Tata Solar, Vikram Solar, Waaree. Adding any future brand is then one INSERT row — no code deploy needed. Every product links to brands.id as a foreign key, not a free-text field.
Per-product GST override (not per-brand, per-product)
The Eastman 12% vs Luminous 18% PCU disagreement proves that category-level GST defaults are only a starting point. The product form must show the auto-default from the category but allow the user to override it per product. When a product's GST rate differs from the category default, show a visible warning: "Non-standard rate — verify with CA before invoicing."

Phase 1 — Schema Foundation
Effort: ~2 hours | Risk: Very Low
Goal: Add all new columns and tables. Every new column is either NULL or has a default value — zero risk of breaking existing modules.
Task 1.1 — Create brands table in shared/schema.ts
Fields: id (UUID), name (VARCHAR 100), defaultMarginPct (DECIMAL 5,2), gstOverrideAllowed (BOOLEAN DEFAULT true), notes (TEXT NULL). Seed with Eastman, Luminous, Adani Solar, Tata Solar, Vikram Solar, Waaree.
Task 1.2 — Add new columns to products table

warrantyPeriod VARCHAR(50) NULL — e.g. "5 Years", "60+60 Months", "25 Years"
mrp DECIMAL(10,2) NULL — Luminous products have MRP; Eastman does not
specs JSONB NULL — flexible key-value spec bag per product
serialTracked BOOLEAN DEFAULT false — for batteries and panels that need serial number capture
packSize INTEGER NULL — panels and accessories ship in fixed pack sizes
almm BOOLEAN NULL — ALMM list approval (Solar Panels only)
dcrCompliant BOOLEAN NULL — DCR compliance (Solar Panels only)
brandId UUID NULL REFERENCES brands(id) — foreign key to brands table

Do NOT remove or rename any existing columns.
Task 1.3 — Add customerType to customers table
customerType VARCHAR(20) DEFAULT 'end_user'. Valid values: distributor, dealer, end_user, project, govt. This is the prerequisite for MRP ceiling enforcement in Phase 4.
Task 1.4 — Run db:push and smoke test
After pushing schema, start the dev server and confirm all of these still work: Products list, Sales order / quotation line item product selection, Daily Pricing page, Inventory GRN page. If anything breaks, roll back the new columns and investigate before continuing.

Phase 4 — Sales Module Integration
Effort: ~3 hours | Risk: Low
Goal: Surface MRP, ALMM status, and warranty in the sales and quotation flows.
Task 4.1 — MRP ceiling hint in Sales line item
When the user enters a unit price on a quotation or sales order line item, check against the product's MRP. If selling price > MRP and customer type is end_user, show a red warning: "Above MRP — end customer pricing." If customer type is dealer or distributor, show it as an informational note only (not an error). Do not hard-block yet — just warn.
Task 4.2 — ALMM/DCR flag on quotation line item
When a Solar Panel product is added to a quotation, show small chips: ALMM ✓ or ALMM ✗, DCR ✓ or DCR ✗. If the sales order is tagged as a subsidy scheme (PM Surya Ghar, MNRE Rooftop etc.) and the selected panel is not ALMM approved, show a blocking warning: "This panel is not on the ALMM list — the customer's subsidy application will be rejected. Please select an ALMM-approved panel."
Task 4.3 — Warranty on quotation PDFs
Include warrantyPeriod in the jsPDF line item section. Format: show below the product description as "Warranty: 5 Years Manufacturer Warranty." Only show if warrantyPeriod is not blank.

Phase 5 — Bulk CSV Import
Effort: ~1.5 days | Risk: Low
Goal: Allow importing 300+ products from a CSV file so the team does not enter them one by one. This must be done before loading the Eastman and Luminous catalogs.
Task 5.1 — POST /api/products/import endpoint in server/routes.ts
Accepts: multipart/form-data with a CSV file.
CSV columns (all optional except name and category):
name, sku, brand, category, description, unitPrice, gstRate, hsnCode, unit, minStockLevel, minMarginPct, warrantyPeriod, mrp, type, serialTracked, packSize, almm, dcrCompliant, specs (JSON string)
Processing rules:

Parse row by row
Validate: name and category must be present; category must match the 16-item list; brand must exist in the brands table (create it if it doesn't exist)
If SKU already exists in the database: skip and add to skipped list — never overwrite
If SKU is blank: auto-generate from brand + name + timestamp
Insert all valid rows in a single transaction
Return: { imported: N, skipped: M, errors: [ { row: N, reason: "..." } ] }

Task 5.2 — Download Template button
Generates a sample CSV with all columns listed above. Include one example row per major category type so the person preparing the file knows the expected format for each field. This template is what your team uses for every new brand — paste from their PDF into the template, clean up, import.
Task 5.3 — Import UI in Products page
Add an "Import CSV" button next to the existing "+ Add Product" button. Opens a dialog with: file picker (CSV only), Download Template link, a column preview/validation step before confirming import, results summary (Imported N / Skipped M), and a downloadable error report if any rows failed.
Task 5.4 — Serial number capture at GRN
For products with serialTracked = true, when a GRN line item is saved, prompt for serial numbers — one per unit received. Store in a new table product_serials: id, productId, grnId, serialNumber, status (in_stock / sold / returned / defective), createdAt. This cannot be added retroactively — once you receive stock without serial capture, warranty claims become unverifiable.

Phase 6 — Bundle / Kit Engine
Effort: ~2–3 days | Risk: Medium
Goal: Handle Solar BOS Kit, all 55+ Eastman Lith Combo products, and all 500+ Luminous SPGS combos properly — with automatic stock deduction from components when a bundle is sold.
Interim workaround (use until Phase 6 is built): Enter BOS Kit as a single product with a fixed price. Enter each Lith Combo and SPGS combo as a separate product SKU at the combo price. Stock will not auto-deduct from components — track manually. This is clunky but functional and does not block catalog loading.
Task 6.1 — product_bundle_items table
Fields: id (UUID), parentId (UUID REFERENCES products.id), componentId (UUID REFERENCES products.id), quantity NUMERIC(10,3), unit VARCHAR(20). Add 'bundle' as a valid value for products.type alongside existing 'product' and 'service'.
Task 6.2 — Bundle components UI in product dialog
When product type = bundle, show a Components section in the product form. Add/remove component rows, each with a product selector, quantity, and unit. Add a Pricing Mode toggle: Manual (fixed price set on the bundle) or Auto-calculated (sum of component effective prices). Both modes must be supported — BOS Kit uses Manual; SPGS combos can use Auto.
Task 6.3 — Stock deduction logic
When a bundle is added to a Sales Order or dispatched, stock deducts from each component product — not from the bundle itself. The bundle has no stock record of its own. When any component is out of stock, show a warning on the quotation: "Insufficient stock — [Component Name] is out of stock."
Task 6.4 — Bundle price freshness (nightly job)
For all auto-priced bundles, run a nightly recalculation of the derived price from current component effective prices. If any bundle's computed price has moved more than 2% from the previous day, flag it in the Daily Pricing Review screen. This handles the Luminous SPGS 500+ combo situation automatically — you do not need to manually update 500 combo prices every time a component price changes.
