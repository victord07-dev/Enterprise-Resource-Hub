Phase 4B: Cash & Bank Account Ledger

CONTEXT

Phase 4A is closed. The system tracks customer payments, supplier
payments, and expenses correctly per-counterparty (customer/supplier),
but has no concept of WHICH bank account or cash box money flows
through. CEO can see "₹X total revenue" but not "₹Y came into HDFC,
₹Z came into ICICI."

This phase fills the structural gap by adding cash_accounts as
first-class entities, links every payment and expense to a specific
account, and provides per-account balance and transaction visibility.

What this phase delivers:
- cash_accounts table with admin-managed CRUD (4 seed accounts:
  HDFC, ICICI, AXIS, CEO Cash)
- cash_account_id FK on customer_payments, supplier_payments, expenses
- Account selection required on all payment + expense forms going
  forward
- Account-to-account transfer feature (rare but needed)
- Balance adjustment entries (admin/accountant only, with reason)
- Cash Position page showing all accounts + per-account drill-down
- Date range filters: today / week / month / quarter / year / custom
- Opening balance editable per account (so CEO can set real values
  at production go-live time)

What this phase does NOT deliver (Phase 4C):
- Financial dashboard widgets (revenue, top customers, etc.)
- Cross-account reports beyond basic cash position
- Cash flow forecasting / predictive analytics

SECTION A — SCHEMA ADDITIONS
==========================================================

A1. New table cash_accounts:
    id (uuid PK, default gen_random_uuid())
    name (text, NOT NULL, unique)
    -- e.g., "HDFC Bank", "ICICI Bank", "AXIS Bank", "CEO Cash"
    type (text, NOT NULL)
    -- Allowed values: 'bank' | 'cash'
    account_number (text, nullable)
    -- Optional, only meaningful for bank accounts
    opening_balance (numeric, NOT NULL, default 0)
    opening_balance_date (timestamp, NOT NULL, default now())
    is_active (boolean, NOT NULL, default true)
    notes (text, nullable)
    created_at (timestamp, NOT NULL, default now())
    updated_at (timestamp, NOT NULL, default now())

A2. New table account_transfers:
    id (uuid PK)
    from_account_id (uuid FK → cash_accounts, NOT NULL)
    to_account_id (uuid FK → cash_accounts, NOT NULL)
    -- DB constraint: from_account_id != to_account_id
    amount (numeric, NOT NULL, > 0)
    transfer_date (timestamp, NOT NULL, default now())
    reference (text, nullable)
    -- Free-text reference (e.g., "Cash deposit at branch", "NEFT TXN12345")
    notes (text, nullable)
    created_by (uuid FK → users, NOT NULL)
    created_at (timestamp, NOT NULL, default now())

A3. New table balance_adjustments:
    id (uuid PK)
    cash_account_id (uuid FK → cash_accounts, NOT NULL)
    adjustment_amount (numeric, NOT NULL)
    -- Signed: positive = increase balance, negative = decrease
    adjustment_date (timestamp, NOT NULL, default now())
    reason (text, NOT NULL)
    -- Mandatory free-text reason (e.g., "Bank fee debit",
    -- "Interest credit", "Reconciliation correction")
    adjusted_by (uuid FK → users, NOT NULL)
    created_at (timestamp, NOT NULL, default now())

A4. Add cash_account_id (nullable initially, NOT NULL after backfill)
    to existing tables:
    - customer_payments: cash_account_id (uuid FK → cash_accounts)
    - supplier_payments: cash_account_id (uuid FK → cash_accounts)
    - expenses: cash_account_id (uuid FK → cash_accounts)

A5. Run db:push.

SECTION I — BALANCE COMPUTATION LOGIC
==========================================================

I1. Backend helper function (reusable):
    storage.computeAccountBalance(accountId, asOfDate?)
    
    Returns: numeric (current balance as of asOfDate, defaults to now)
    
    Computation:
    balance = account.opening_balance
            + SUM(customer_payments.amount WHERE cash_account_id = X
                  AND payment_date <= asOfDate)
            + SUM(account_transfers.amount WHERE to_account_id = X
                  AND transfer_date <= asOfDate)
            + SUM(balance_adjustments.adjustment_amount WHERE
                  cash_account_id = X AND adjustment_date <= asOfDate)
            - SUM(supplier_payments.amount WHERE cash_account_id = X
                  AND payment_date <= asOfDate)
            - SUM(expenses.amount WHERE cash_account_id = X
                  AND expense_date <= asOfDate)
            - SUM(account_transfers.amount WHERE from_account_id = X
                  AND transfer_date <= asOfDate)

I2. For date range views:
    storage.computeAccountStats(accountId, fromDate, toDate)
    
    Returns: {
      openingBalance: number,    // computeAccountBalance(id, fromDate - 1)
      totalInflows: number,      // sum of all incoming in range
      totalOutflows: number,     // sum of all outgoing in range
      netMovement: number,       // inflows - outflows
      closingBalance: number,    // computeAccountBalance(id, toDate)
      transactionCount: number
    }

I3. For unified transaction history:
    storage.getAccountTransactions(accountId, fromDate, toDate, limit, offset)
    
    Returns array of unified transaction objects from all 5 sources
    (customer_payments, supplier_payments, expenses, transfers in,
    transfers out, adjustments) with running balance computed.

I4. No snapshot table for now. All computed on-the-fly. ITFI scale
    (₹2 Cr/month, ~150-450 transactions/month) supports this without
    performance issues. Add snapshots in future phase if year-end
    queries become slow.
